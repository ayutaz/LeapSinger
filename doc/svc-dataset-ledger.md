### ここから読み取れる制約

**確認済み: JVS-MuSiC の 24 kHz は本プロジェクトの mel 設定と整合しません。** `mel.fmax` は
16,000 Hz、`mel.sr` は 44,100 Hz です。24 kHz 音源の Nyquist は 12 kHz なので、**12〜16 kHz の
mel bin が常に空**になります。これを混ぜて学習すると、その帯域を「無い」と学習してこもった出力に
なります。話者数 100 は魅力的ですが、そのままでは multi-singer corpus に使えません。
帯域制限を承知で低域だけに使うか、除外するかの判断が要ります。

**確認済み: GTSinger は非商用（NC）かつ継承（SA）です。** 日本語を含み 80.59 時間、技法ラベル
6 種（mixed voice / falsetto / breathy / pharyngeal / vibrato / glissando）付きで、規模と内容は
最有力です。一方 **CC BY-NC-SA は MERT を不採用にしたのと同じ理由で商用配布と衝突**します。
さらに ShareAlike が学習済みモデルの重みに及ぶかは条文から読み取れません。

**確認済み: VocalSet は CC BY 4.0 で、いま調べた中で唯一「商用利用可・帰属表示のみ」です。**
20 名 10.1 時間、技法 17 種。ただし a cappella の音階・アルペジオ・ロングトーン・抜粋が中心で、
**歌詞のある楽曲ではありません**。content encoder の学習分布としては音素の偏りが大きく、
multi-singer corpus 単独としては不足します。技法の網羅性は随一なので、**評価用や技法補強**に向きます。

**技法ラベルの副次的な価値:** GTSinger か VocalSet を使う場合、M0 ゴール 3 の「発声スタイルの
coverage」が**自動で集計できます**。現在 `preprocess/svc/coverage.py` はラベルが無いため音域しか
出せません。

**GTSinger の倫理条項（確認済み）:** README は「本人の同意なく特定個人の歌声を生成すること」を
明示的に禁じています。SVC はまさにその技術なので、**target singer の同意**が前提になります。

**帯域チェックを検査に追加しました。** GTSinger 自身が `check_valid_bandwidth.py` を同梱している
ことから分かるとおり、「宣言された sample rate より実際の帯域が狭い素材」は実在します。
`preprocess/svc/audit.py` の `effective_bandwidth_hz()` で実際の上限周波数を測り、
`AuditThresholds(min_bandwidth_hz=16000.0)` を渡すと `band_limited=...` として弾きます
（既定は無効。純音のような合成信号を誤検出しないため）。

### 実データで見つかった欠陥と修正

**確認済み:** 歌手単位でランダムに held-out を選ぶと、**性別が極端に偏りました。**

| seed | 層化なし（修正前） | 層化あり（修正後） |
|---|---|---|
| 0 | eval=男男 / test=男男 | eval=女男 / test=女男 |
| 1 | eval=男男 / test=女男 | eval=女男 / test=女男 |
| 2 | eval=女男 / test=女女 | eval=女男 / test=女男 |
| 3 | eval=女女 / test=女女 | eval=女男 / test=女男 |

SVC は異性間の変換が難所なので、held-out が片方の性別だけだと**評価がその難所を素通り**します。
`split_by_group()` に `strata` 引数を追加し、層をラウンドロビンで配ることで held-out に必ず
各層が混ざるようにしました。**素材が決まったら性別で層化して split を作ります。**

### 実音声での検査（M0 ゴール 2）

**確認済み:** リポジトリ内の実歌唱（`demo/audio/*_gt.ogg` と
`notebooks/sample_data/ritsu_flashblack_0000.wav`、3 DB 分の 17 クリップ・99.5 秒・15 曲）に
検査を通しました。全件 44.1 kHz です。

| 設定 | 受理 | 除外 | 除外理由 |
|---|---:|---:|---|
| 既定（帯域チェックなし） | 17 | **0** | — |
| `min_bandwidth_hz=16000` | 13 | **4** | すべて `band_limited`（15,668〜15,702 Hz） |

**確認済み: 弾かれた 4 件の遮断周波数は 15.67〜15.70 kHz にそろっています。** これは
**Ogg Vorbis の非可逆圧縮の痕跡**で、素材の欠陥ではなく配布形式の性質です。`mel.fmax` が
16,000 Hz なので、この素材で学習すると最上位の mel bin が常に減衰した状態になります。

**この結果の読み方（重要）:** `demo/audio/` は**デモ用に ogg へ圧縮した抜粋**であり、
元の歌声 DB そのものではありません。したがってこの reject list は
**検査が実音声で機能することの実証**であって、3 DB の素材に対する判定ではありません。
実素材で流すときは、非圧縮の原本に対して `min_bandwidth_hz=16000` で検査します。

**副次的な確認:** 帯域チェックを入れない既定設定では 17 件すべてが通りました。clipping・
無音・DC offset・長さの閾値が、実際の歌唱に対して過剰に厳しくないことの確認になります。

### VocalSet 全件（音声 3,613 件）を通した結果

**確認済み:** `VocalSet11.zip`（1,981 MB、Zenodo 1442513、CC BY 4.0）を取得し、全 3,613 wav
（**44.1 kHz / mono / PCM_16**）に検査・coverage・split を通しました。**実データが 4 つの
問題を暴いたので、順に記録します。**

| 項目 | 値 |
|---|---|
| 受理 / 除外 | **3,573 / 40**（除外はすべて `clipping`） |
| 受理時間 | **8.73 時間** |
| 歌手 | **20 名**（female1–9 / male1–11） |
| 技法 | **17 種** |

#### 問題 1: 歌手 ID をファイル名から取ると leakage する

`FULL/<歌手>/<種別>/<技法>/<file>.wav` という構造ですが、**32 件はファイル名に歌手接頭辞が
ありません**（例: `FULL/female2/arpeggios/lip_trill/lip_trill_arps.wav`）。さらに
**`male8` ディレクトリに `m9_` で始まるファイルが 1 件**あります。

ファイル名から歌手を取ると、同一人物が `female2` と `f2` の 2 つの ID に分かれ、
**held-out にしたはずの歌手が train にも入ります。** 最初の集計では歌手が 27 名に見えていました
（正しくは 20 名）。**ディレクトリ名を歌手 ID の唯一の正とします。**

#### 問題 2: 技法ラベルに表記ゆれがある

`vibrato`（255 件）と **`vibrado`（6 件）** が別ディレクトリとして存在します。コーパス側の
誤記です。正規化しないと vibrato を過小に数え、存在しない技法が 0.5% として現れます。
技法は 18 種に見えていましたが、正規化して **17 種**です。

#### 問題 3: `min_bandwidth_hz=16000` は実歌唱に対して厳しすぎる（推奨を撤回）

3 節で「実音声には `mel.fmax` と同じ 16000 を推奨」と書きましたが、**実測で否定されました。**

| 実効帯域 | p05 | p25 | p50 | p75 | p95 |
|---|---:|---:|---:|---:|---:|
| VocalSet 603 件抽出 | 10,355 | 13,456 | **15,996** | 22,026 | 22,026 Hz |

16,000 Hz で切ると **51% が落ちます**（実際 1,915 件が `band_limited` になりました）。
しかし **p75 と p95 が Nyquist（22,026 Hz）に達している**ので、このコーパスは帯域制限されて
いません。母音の伸ばしは高域が薄く、息や摩擦音は Nyquist まで届く、という**内容による差**です。

**訂正した方針:** 帯域チェックは**1 クリップの合否判定に使わない**。コーパス全体の分布で見て、
p75 / p95 が Nyquist 付近なら full-band、分布全体が特定周波数で頭打ちならその sample rate から
上げた素材、と判定します。`preprocess/svc/audit.py` の説明も修正しました。

#### 問題 4: 全長 1 回の FFT は素因数によって極端に遅い

`effective_bandwidth_hz` が信号全長で FFT を取っていたため、長さが大きな素因数を持つファイルで
処理が跳ね上がり、3,613 件で 10 分を超えました。固定長 8,192 の窓へ切って平均する方式に変え、
**4.1 分 → 0.6 分（6.6 倍）**になりました。窓を平均する分、ビンごとの暴れも減ります。

#### 技法 coverage（正規化後・受理分のみ）

straight 13.7% / slow_piano 13.3% / slow_forte 12.2% / vibrato 11.3% / vocal_fry 6.5% /
breathy 5.3% ほか。

#### 層化 split

`eval = [female9, m11]`、`test = [f7, m7]` のように**全 seed で男女が混ざる**ことを確認済みです。

### GTSinger 日本語分の実測（2026-08-30）

**確認済み:** HF から `Japanese/**` を取得し、無作為 50 件の仕様と検査結果を測りました
（取得は継続中）。

| 項目 | 実測値 |
|---|---|
| 仕様 | **48,000 Hz / mono / PCM_24** |
| 1 クリップの長さ | 平均 10.4 秒 |
| 実効帯域 | p05 14,526 / p50 **17,036** / p95 22,160 Hz（Nyquist 24,000） |
| 既定閾値での除外 | **0 / 50 件** |
| 付属物 | `.wav` に加えて **TextGrid（音素アライメント）/ json / musicxml（譜面）** |

**確認済み: README の「48 kHz / 24-bit」は実測と一致します。** 帯域も VocalSet（p50 15,996 Hz）
より高く、44.1 kHz へ落としても `mel.fmax` 16,000 Hz まで実体があります。**帯域の面では
base corpus に適します。**

**パス構造:** `Japanese/<歌手>/<技法>/<曲名>/<Control_Group | ..._Group>/<連番>.wav`。
歌手・技法・曲・対照群がすべてパスから取れます。**`Control_Group` は技法を適用しない対照**で、
同じ曲の技法あり/なしが対になっています。split は**曲単位**で切ります。

**注意:** HF の tree API は `recursive=true` でも一部しか返しませんでした（187 件と報告されたが
実際は 1,600 件以上）。**API の件数を素材量の根拠にしないこと。**

#### 付属注釈が非常に厚い（M0 ゴール 3 を音素単位で満たせる）

**確認済み:** 各 wav に同名の `.json` / `.TextGrid` / `.musicxml` が付きます。json は**語単位の配列**で、
1 要素が次を持ちます。

- `ph` / `ph_start` / `ph_end` — **音素とその時刻**（アライメント済み）
- `note` / `note_dur` / `note_start` / `note_end` — **音符**
- `mix` / `falsetto` / `breathy` / `pharyngeal` / `glissando` / `vibrato` — **音素ごとの技法フラグ**
- `singing_method` / `pace` / `range` / `emotion` — 全体属性

TextGrid の tier も `word / phone / mix / falsetto / breathy / pharyngeal / vibrato / glissando / global`
です。**発声スタイルの coverage を、ファイル単位ではなく音素単位の滞在時間で出せます。**

#### 実際に leakage を検出した（M0 ゴール 4 の要）

**確認済み:** 3 音源は**同一歌手が同じ曲を違う歌い方で歌ったもの**です。曲フォルダ名は
`GraveKeeper-3_normal`（kire 側）と `GraveKeeper_soft` のように音源ごとに異なるため、
**フォルダ名をそのまま group にすると同じ曲が別々の group として扱われます。**

実測: 曲フォルダは 100 種ありますが、`±N 半音` と `_normal` / `_soft` / `_kire` の接尾辞を
落として正規化すると **75 曲**で、**50 曲が複数音源に跨って**います。
フォルダ名のまま seed 0 で split したところ、**`GraveKeeper` が train と test の両方に入りました。**

**同じ歌手が同じ曲を歌ったものが train と test に分かれると、汎化性能を過大評価します。**
接尾辞を落とした曲名を group にすれば解消します（正規化後は 75 group で leakage 0）。

**決定:** 波音リツを使うときは、**曲名を `[+-]\d+$` と `_(normal|soft|kire)$` で正規化してから
split** します。M0 ゴール 4 が「曲単位・収録セッション単位で分離」と書いているのは、
まさにこの種の取り違えを防ぐためです。

### sample rate が 3 種類に分かれる（前処理の要件）

**確認済み:** 44,100（リツ・VocalSet）/ 48,000（GTSinger・夏目）/ **96,000（くるみ）** が混在します。
`mel` セクションは前処理・loader・励起で共有され常に一致していなければならないので、
**前処理の入口で全部 44,100 Hz へ揃えます。** `mel.fmax` は 16,000 Hz、どのコーパスも
実効帯域 p50 が 16,000 Hz 以上あるため、44.1 kHz へ落としても必要な帯域は失われません。

### 無音閾値は曲全体のファイルに合わない（閾値の校正）

**確認済み:** 夏目悠李で 6 件が `silence`（55〜76%）で落ちました。しかしこれらは**曲全体を
1 ファイルにしたもの**で、前奏・間奏・後奏を含むため無音率が高いのは正常です。
`AuditThresholds.max_silence_ratio = 0.5` は**フレーズ単位のクリップを想定した値**です。

**決定:** 曲全体のファイルを検査するときは無音閾値を上げるか、**phrase 分割の後に検査**します。
既存の `preprocess/run.py` は phrase 分割を行うので、SVC 前処理でも分割後に検査する方が
実態に合います。

### 帯域チェックの再確認（96 kHz 素材）

御丹宮くるみは 96,000 Hz ですが実効帯域 p95 は 18,111 Hz です。**これは帯域制限ではなく、
歌声にそもそも 18 kHz より上のエネルギーがほとんど無いためです。**`mel.fmax` 16,000 Hz を
上回っているので問題ありません。3 節・4 節で確立した「1 クリップで判定せず分布で見る」
という方針が、ここでも正しく働きました。

### これが素材選定に与える含意（重要）

**仮説:** 本パイプラインは mel を NHVSing に渡して波形にします。**NHVSing が見たことのない

base に選べば、音響モデルの出力 mel が vocoder にとって in-distribution に保たれます。

これは 6 節の選定（base = GTSinger）と**競合します**。GTSinger は NHVSing の学習に
使われていません。トレードオフは次のとおりです。

| 選択 | 利点 | 懸念 |
|---|---|---|
| **GTSinger 中心** | 80.6 h・20 歌手・48 kHz の実録音。日本語含む 9 言語、技法ラベル | NHVSing にとって未知の音色。vocoder 側の劣化リスク |
| **NHVSing 学習セット中心** | mel が vocoder に in-distribution。日本語 5 種（きりたん・夏目・リツ・くるみ・No.7） | 個々が小規模。要ログインのものが 2 件。歌手数を稼ぎにくい |

**実施済み（下の 7b 節）。** 結論は「**GTSinger に out-of-distribution なペナルティは見えない**」で、
6 節の選定（base = GTSinger）と競合しません。

## 7b. NHVSing にとって in-distribution かの実測（2026-08-30）

**確認済み（M0 ゴール 4）:** 測定は [`tools/nhv_indist.py`](../tools/nhv_indist.py)、
生データは `.m0data/nhv_indist/nhv_indist.json` です。

**測り方:** 音響モデルを介さず、**ground-truth mel をそのまま NHVSing に通した再合成**の忠実度を
比べます。音響モデルを挟むと劣化が vocoder 由来か音響モデル由来か分かりません。各コーパスから
**曲が偏らないように 12 clip・各 6 秒**を決定的に選び（seed 0）、有声率 0.3 未満の窓は
前処理本体と同じ扱いで除外しました。指標は原音 mel と再合成 mel の L1、再合成から取り直した
F0 の半音誤差、V/UV 一致率です。

| コーパス | NHVSing 学習 | clips | mel L1 平均 | 中央値 | 標準偏差 | p95 | F0 半音 | V/UV |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 波音リツ | あり | 12 | 0.3470 | 0.3320 | 0.045 | 1.112 | 0.019 | 0.989 |
| 夏目悠李 | あり | 12 | 0.2969 | 0.3013 | 0.051 | 0.904 | 0.025 | 0.981 |
| 御丹宮くるみ | あり | 12 | 0.3306 | 0.3344 | 0.032 | 0.939 | 0.013 | 0.994 |
| VocalSet | あり | 12 | 0.3020 | 0.3062 | 0.033 | 0.870 | 0.013 | 0.991 |
| **GTSinger 日本語** | **なし** | 12 | **0.3444** | 0.3441 | 0.031 | 0.962 | 0.017 | 0.990 |

**判断: GTSinger を base に選んでよい。** 根拠は 2 つです。

1. **GTSinger は外れ値ではありません。** その平均 0.3444 は、NHVSing 既知 4 コーパスの平均が
   散らばる範囲（0.2969〜0.3470）の**内側**にあり、**target singer である波音リツ（0.3470、
   NHVSing 既知）より良い**値です。F0 誤差も V/UV 一致率も同水準です。
2. **既知/未知よりコーパス間の差のほうが大きい。** 既知 4 コーパスどうしの最大差は +16.9%
   （夏目 0.2969 対 リツ 0.3470）で、既知をまとめた平均（0.3191）と GTSinger の差 +7.9%
   （Mann-Whitney U で p = 0.034）より大きい。差の主因は「NHVSing が見たかどうか」ではなく
   コーパスの性質だと読めます。

したがって、条件付きトラック (B)「NHVSing target fine-tune」を**今の時点で起動する根拠はありません**
（[実行計画](svc-plan.md) 7 節の起動条件も満たしていません）。

**この測定の限界（重要）:**

- **ground-truth mel の再合成であって、音響モデルが出す mel の分布ではありません。** 学習後の
  モデルが出す mel が vocoder にとって扱いにくい可能性は、これでは否定できません。M4 の後に
  同じ道具で測り直します。**（2026-09-01 時点で M4 は完了しましたが、この測り直しは未実施です。）**
  なお M3 / M4 では、`tools/m3_verify.py` が「GT mel の再合成」を上限としてモデル出力と比べる
  形で部分的に代替しています。
- GTSinger は**日本語 2 歌手・12 clip**です。全 9 言語 20 歌手の代表とは言えません。
- clip 数 12 での比較で、効果量の小さい差を検出できる設計ではありません。
- 対照の VocalSet は「別コーパスだが NHVSing 既知」として置きました。これが既知側に収まった
  （0.3020）ことは、差が収録の異質さだけで決まるのではないことを支持します。
- **この計測は bit 再現しません。** 同じ引数で 2 回目を回すと、各セットの平均 mel L1 は
  最大 **0.0074** 動きました（リツ 0.3470→0.3482、くるみ 0.3306→0.3232、GTSinger
  0.3444→0.3453）。clip の選択も窓の位置も seed で固定しているので、原因は
  onnxruntime と torch の CPU 実行です。**ゆらぎはコーパス間の差（0.050）より小さく、
  順位も判断も変わりません**が、この桁の差を根拠にした議論はできません。
